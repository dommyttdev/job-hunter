# 0006 求人状態イベントと利用者向け発見を分離する

- 状態: Accepted

## 背景

同じ求人は複数利用者・複数監視設定の検索結果に現れる。監視設定ごとに更新・削除イベントを作ると、同じ求人状態の変化が重複し、同じ利用者が重なる検索条件を登録した場合に重複通知が生じる。一方、新着は求人自体の状態ではなく、初回基準化後に各利用者が初めて観測した事実である。

## 決定

- `UPDATED`、`DELETED`、`RELISTED`は、`(source_key, external_job_id)`で識別する求人単位の状態イベントとして1件だけ作成する。
- `DISCOVERED`は利用者と求人の組に対する利用者向け発見イベントとして1件だけ作成する。
- 監視設定は必ず1人の利用者が所有する。
- イベントと該当監視設定の関連はイベント本体から分離し、複数の監視設定を関連付けられるようにする。
- 同じ利用者の複数監視設定に同じ求人が該当しても、利用者向け発見イベントと通知は重複させない。

## 代替案

- 監視設定ごとに全イベントを作る方式: 実装は単純だが、求人状態イベントと通知が重複するため採用しない。
- 全イベントを求人単位にする方式: 更新・削除には適するが、利用者ごとに異なる発見時点を表現できないため採用しない。
- 利用者ごとに全イベントを作る方式: 通知処理は単純になるが、同じ求人状態の事実とHTML版を利用者数だけ複製するため採用しない。

## 影響

- 求人状態、HTML版、状態イベントを利用者間で共有しながら、利用者ごとの発見と通知処理を分離できる。
- イベント、監視設定、利用者別通知項目の関連を明示する中間データが必要になる。
- 利用者や監視設定を削除しても、他利用者が参照する求人状態イベントを維持できる。
