# 0002 Flask、Jinja2、SQLAlchemy、SQLiteを採用する

- 状態: Accepted

## 背景

初期リリースでは、監視URLを管理する小規模なWeb画面と、同じドメインロジックを利用する定期処理が必要である。運用対象を少なく保ち、単一ホストで開始できる構成が望ましい。

## 決定

- フロントエンドはJinja2によるサーバーサイドレンダリングとする。
- バックエンドはPythonのFlaskとする。
- 永続化はSQLAlchemyを介したSQLiteとする。
- Web処理と定期処理は同じPythonパッケージのアプリケーションサービスを利用する。
- 定期処理はHTTPリクエストから分離し、複数ワーカーで外部処理を並行実行する。

SQLiteの利用中は、WAL、foreign key enforcement、`busy_timeout`、短いトランザクションを運用条件とする。複数ワーカーからの書き込み要求は許容するが、書き込みトランザクションはSQLiteによって直列化されることを前提とする。`SQLITE_BUSY`は冪等な作業単位で上限付き再試行を行う。

## 代替案

- SPAフレームワークとAPI: 画面の独立性は高いが、現時点の設定・履歴閲覧画面にはビルド、状態管理、API設計のコストが過剰なため採用しない。
- Django: 管理画面やORMを統合できるが、採用済みのFlaskとSQLAlchemyによる小さな構成を優先する。
- PostgreSQL: 高い書き込み並行性と運用機能を持つが、初期の単一ホスト構成では外部DB運用を増やすため採用しない。
- SQLAlchemyを使わない直接SQL: 依存は減るが、Session境界、モデル関係、将来のDBMS移行を一貫して管理しにくいため採用しない。

## 影響

- テンプレート、route、アプリケーションサービス、永続化の境界を明示する必要がある。
- 外部HTTP取得とCodex CLI実行は複数ワーカーで並行化できるが、DB書き込みは1トランザクションずつ確定する。
- ワーカー並列度が高すぎるとロック待ちと`SQLITE_BUSY`が増えるため、メトリクスに基づく上限設定が必要になる。
- DBをネットワーク共有上へ配置できず、Webとワーカーは同一ホストで動かす。
- Jinja2の自動エスケープを無効化せず、求人HTMLは管理画面へ直接描画しない。
- 高負荷化した場合、SQLAlchemyだけで差異が完全に吸収されるとは仮定せず、DBMS移行用ADRと互換性テストが必要になる。
