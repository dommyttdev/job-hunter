# 求人変更監視

- 状態: Draft
- 対象: 求人検索URLの定期監視と変更通知

## 目的

利用者が登録した求人サイトの検索結果を定期的に確認し、求人の新着、内容更新、掲載削除を検知して通知する。求人サイト固有のHTML構造を中核処理から分離し、サイト追加時の変更範囲を限定する。

## 対象範囲

- 利用者による対応済み求人サイトの検索結果URLの登録、停止
- 検索結果の全ページからの求人IDと求人詳細URLの取得
- 求人詳細ページから抽出した求人固有HTML、比較用ハッシュ、取得履歴の保存
- 新着、更新、削除の検知
- Codex CLIによる新着内容または更新差分の要約
- 検知結果の通知と配信再試行

## 対象外

- 求人内容を項目別に構造化して保存、検索する機能
- 求人サイトへの応募、ログイン情報の代行入力
- 異なる求人サイト間で同一求人を名寄せする機能
- ログインが必須の求人サイトへの初期対応

## ユースケース

1. 利用者は検索結果URLを登録する。
2. システムはURLを担当できる求人サイトアダプターを特定し、定期監視を開始する。
3. システムは初めて監視対象に現れた求人を新着として通知する。
4. システムは保存済み求人の詳細ページが実質的に変化したとき、変更前後を要約して通知する。
5. システムは詳細ページで掲載終了を確認したとき、求人を論理削除して通知する。

## 機能要件

| ID | 要件 |
| --- | --- |
| FR-001 | 対応済みサイトの検索結果URLだけを監視対象として登録できる。 |
| FR-002 | 監視対象ごとに確認・通知間隔を12時間または24時間から設定できる。 |
| FR-003 | 通常リンク、form、無限スクロールを含む検索結果の全ページをたどり、求人IDと正規化した詳細URLを重複なく取得する。 |
| FR-004 | 求人の同一性を求人サイト識別子とサイト内求人IDの組で判定する。 |
| FR-005 | 求人が監視対象に初めて出現した場合、詳細ページから求人固有領域だけを抽出・正規化し、そのHTMLと比較用ハッシュを保存して新着イベントを生成する。 |
| FR-006 | 掲載中求人の詳細URLを定期取得し、求人固有HTMLのハッシュが直前の版と異なる場合、そのHTMLの新しい版と更新イベントを保存する。 |
| FR-007 | HTTP 404またはサイト固有の掲載終了表示を確認した場合、求人を論理削除し、削除イベントを保存する。 |
| FR-008 | 通信失敗、HTTP 401、403、429、5xx、解析失敗だけでは求人を削除扱いにしない。 |
| FR-009 | 新着では現在のHTML、更新では変更前後のHTMLをCodex CLIへ渡し、通知用の要約を生成する。 |
| FR-010 | 変更イベントと要約を利用者の通知先へ配信し、同じイベントの重複通知を抑止する。 |
| FR-011 | 停止中の監視対象は検索結果を取得せず、その監視対象だけを理由に求人状態を変更しない。 |
| FR-012 | 論理削除済み求人が再び有効な詳細ページとして確認された場合、再掲載として新しい版とイベントを生成する。 |
| FR-013 | Google OpenID Connectで利用者を認証し、初回認証時に会員登録して利用者を作成する。 |
| FR-014 | ログイン方式は型付き認証プロバイダーを追加して拡張できる。 |
| FR-015 | 利用者は対応済み求人サイトの検索結果URLを追加できる。 |
| FR-016 | 利用者は監視対象ごとに確認・通知間隔を12時間または24時間から選択できる。 |
| FR-017 | 利用者は自分の監視対象に関連する求人情報、要約、変更履歴、掲載状態を閲覧できる。 |
| FR-018 | Googleログイン済み利用者がLINE通知をONにした場合、LINE Loginによる通知先の本人確認とLINE公式アカウントの友だち追加を促し、通知可能状態を管理する。 |
| FR-019 | 求人変更通知は利用者の画面操作を必要とせず、バックグラウンドで配信する。 |
| FR-020 | 利用者は他利用者の監視設定、求人情報、通知状態を閲覧・変更できない。 |
| FR-021 | 検索結果一覧は新着求人の発見に使用し、一覧から求人IDが消えたことを削除判定に使用しない。 |
| FR-022 | 求人固有領域を抽出できない詳細ページは解析失敗とし、空の求人内容やページ全体を保存しない。 |
| FR-023 | LINE LoginをJobHunterへの会員登録またはログインには使用しない。 |
| FR-024 | LINE通知をOFFにしてもGoogle認証、監視設定、求人履歴を維持する。 |

## 非機能要件

| ID | 要件 |
| --- | --- |
| NFR-001 | 新しい求人サイトは、サイトアダプター、明示的な登録コード、契約テスト用HTMLを追加することで対応できる。 |
| NFR-002 | 取得、変更保存、イベント生成、通知依頼は再実行しても重複する結果を作らない。 |
| NFR-003 | サイト単位の同時実行数、最小アクセス間隔、タイムアウト、再試行を設定できる。 |
| NFR-004 | robots.txt、利用規約、認証要否をサイト追加前に確認し、許可された範囲だけを取得する。 |
| NFR-005 | HTMLを信頼できない入力として扱い、Codex CLIの命令やシステム設定として解釈させない。 |
| NFR-006 | 監視対象、サイト、処理段階ごとに成功数、失敗数、所要時間、キュー滞留を観測できる。 |
| NFR-007 | 変更確定と通知依頼の間でイベントが失われない。 |
| NFR-008 | 共通ヘッダー、フッター、告知、広告など求人と無関係な変更では求人更新を検知しない。 |

## 受入条件

| ID | 条件 |
| --- | --- |
| AC-001 | 各サイト個別仕様に従って求人IDを抽出し、`source_key`との組で求人を一意に保存できる。 |
| AC-002 | 同じ検索結果を複数回処理しても、新着イベントと通知は1件だけである。 |
| AC-003 | 共通ヘッダー、フッター、告知、広告、動的tokenだけが変わったページでは更新と判定せず、求人固有領域が変わった場合は更新と判定する。 |
| AC-004 | 更新通知の要約処理は、直前版と新しい版の両方を参照できる。 |
| AC-005 | 詳細ページの404またはサイトアダプターが掲載終了と判定したページで論理削除され、タイムアウトや429では論理削除されない。 |
| AC-006 | 新規サイトの追加時に、既存の変更検知、要約、通知コンポーネントを変更しない。 |
| AC-007 | GoogleのcallbackとID tokenを検証し、同じGoogle subjectでは同じ利用者としてログインできる。 |
| AC-008 | 検索結果URLと12時間または24時間を登録し、期限に従う取得作業を作成できる。 |
| AC-009 | LINE通知が未連携または利用不能でもGoogleログインと求人閲覧はでき、画面にOFFまたは要対応状態を表示する。 |
| AC-010 | 他利用者のIDを指定したHTTPリクエストで、その利用者のデータを取得・変更できない。 |
| AC-011 | load-more方式の一覧を終了まで処理し、追加表示された求人IDも新着照合対象にできる。 |
| AC-012 | 一覧から既存求人IDが消えても削除せず、詳細ページの404または掲載終了表示で削除する。 |
| AC-013 | 保存した求人HTMLに、詳細ページのヘッダー、フッター、共通告知、広告が含まれない。 |
| AC-014 | Googleログイン済み利用者がLINE通知をONにすると、LINE本人確認と友だち追加の完了後に通知先が有効になる。 |
| AC-015 | LINE callbackだけでは新しいJobHunter利用者を作成できず、Googleログイン済みの連携要求が必要である。 |
| AC-016 | LINE通知をOFFにしてもGoogleログインセッション、監視設定、求人履歴が維持される。 |

## 未決事項

- 既定の監視間隔と詳細ページの再確認間隔
- 求人固有HTML各版、イベント、通知履歴の保持期間
- Codex CLI実行環境、モデル、上限時間、利用量上限
- 初回監視時に既存の全検索結果を新着通知するか、基準データとして通知せず登録するか
