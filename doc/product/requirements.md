# 求人変更監視

- 状態: Draft
- 対象: 求人検索URLの定期監視と変更通知

## 目的

利用者が登録した求人サイトの検索結果を定期的に確認し、求人の利用者向け発見、内容更新、掲載削除を検知して通知する。求人サイト固有のHTML構造を中核処理から分離し、サイト追加時の変更範囲を限定する。

## 対象範囲

- 利用者による対応済み求人サイトの検索結果URLの登録、停止
- 検索結果の全ページからの求人IDと求人詳細URLの取得
- 求人詳細ページから抽出した求人タイトル、求人固有HTML、比較用ハッシュの保存
- 利用者向け発見、更新、削除の検知
- Codex CLIによる発見内容または更新差分の要約
- 検知結果の通知と配信再試行

## 対象外

- 求人内容を項目別に構造化して保存、検索する機能
- 求人サイトへの応募、ログイン情報の代行入力
- 異なる求人サイト間で同一求人を名寄せする機能
- ログインが必須の求人サイトへの初期対応

## ユースケース

1. 利用者は検索結果URLを登録する。
2. システムはURLを担当できる求人サイトアダプターを特定し、定期監視を開始する。
3. システムは初回取得を通知しない基準データとして保存し、その後に利用者の監視結果へ初めて現れた求人を発見として通知する。
4. システムは保存済み求人の詳細ページが実質的に変化したとき、変更前後を要約して通知する。
5. システムは詳細ページで掲載終了を確認したとき、求人を論理削除して通知する。

## 機能要件

| ID | 要件 |
| --- | --- |
| FR-001 | 対応済みサイトの検索結果URLだけを監視対象として登録できる。 |
| FR-002 | 利用者が所有する監視設定ごとに確認・通知間隔を12時間または24時間から設定できる。 |
| FR-003 | 通常リンク、form、無限スクロールを含む検索結果の全ページをたどり、求人IDと正規化した詳細URLを重複なく取得する。 |
| FR-004 | 求人の同一性を求人サイト識別子とサイト内求人IDの組で判定する。 |
| FR-005 | 初回基準化の完了後、求人が利用者の監視結果に初めて出現した場合、詳細ページから求人固有領域だけを抽出・正規化し、そのHTMLと比較用ハッシュを保存して`DISCOVERED`イベントを生成する。同じ求人が同じ利用者の複数の監視設定に該当してもイベントは1件とする。 |
| FR-006 | 掲載中求人の詳細URLを定期取得し、求人固有HTMLのハッシュが直前の版と異なる場合、そのHTMLの新しい版と更新イベントを保存する。 |
| FR-007 | サイト固有の明確な掲載終了表示を1回確認した場合、または間隔を空けた2回の詳細確認で連続してHTTP 404を確認した場合、求人を論理削除し、削除イベントを保存する。 |
| FR-008 | 通信失敗、HTTP 401、403、429、5xx、解析失敗だけでは求人を削除扱いにしない。 |
| FR-009 | 利用者向け発見では現在のHTML、更新では変更前後のHTMLをCodex CLIへ渡し、通知用の要約を生成する。 |
| FR-010 | 変更イベントと要約を利用者の通知先へ配信する。求人状態イベントは求人単位で1件とし、同じイベントを同じ利用者へ重複通知しない。 |
| FR-011 | 停止中の監視設定は検索結果を取得せず、その監視設定だけを理由に求人状態を変更しない。ある求人を参照する有効な監視設定がなくなった場合は、その求人の詳細確認も停止する。 |
| FR-012 | 論理削除済み求人が再び有効な詳細ページとして確認された場合、再掲載として新しい版とイベントを生成する。 |
| FR-013 | Google OpenID Connectで利用者を認証し、初回認証時に会員登録して利用者を作成する。 |
| FR-014 | ログイン方式は型付き認証プロバイダーを追加して拡張できる。 |
| FR-015 | 利用者は対応済み求人サイトの検索結果URLを追加できる。 |
| FR-016 | 利用者は自分の監視設定ごとに確認・通知間隔を12時間または24時間から選択できる。 |
| FR-017 | 利用者は自分の監視設定に関連する求人のタイトル、現在の要約、詳細URL、掲載状態を閲覧できる。過去の変更履歴は提供しない。 |
| FR-018 | Googleログイン済み利用者がLINE通知をONにした場合、LINE Loginによる通知先の本人確認とLINE公式アカウントの友だち追加を促し、通知可能状態を管理する。 |
| FR-019 | 求人変更通知は利用者の画面操作を必要とせず、バックグラウンドで配信する。 |
| FR-020 | 利用者は他利用者の監視設定、求人情報、通知状態を閲覧・変更できない。 |
| FR-021 | 検索結果一覧は利用者向け発見に使用し、一覧から求人IDが消えたことを削除判定に使用しない。 |
| FR-022 | 求人固有領域を抽出できない詳細ページは解析失敗とし、空の求人内容やページ全体を保存しない。 |
| FR-023 | LINE LoginをJobHunterへの会員登録またはログインには使用しない。 |
| FR-024 | LINE通知をOFFにしてもGoogle認証、監視設定、利用者と求人の関連を維持する。 |
| FR-025 | 同じ求人が異なる間隔の複数の有効な監視設定に含まれる場合、詳細ページは最短の間隔で求人単位に1回取得し、取得結果と求人状態イベントを共有する。 |
| FR-026 | 求人状態イベントは検知時に記録し、利用者への通知は該当する監視設定の次回通知時刻まで保留する。同じ利用者の複数の監視設定に該当する場合は1件にまとめる。 |
| FR-027 | 初回基準化で見つかった求人は比較基準として保存し、`DISCOVERED`イベントと通知を生成しない。 |
| FR-028 | 停止した監視設定を再開するときは現在の検索結果と求人状態を通知なしで再基準化し、停止期間中の変化を遡って通知しない。 |
| FR-029 | 求人HTMLは通常、現在版と直前版だけを保持する。未処理または再試行中の通知が参照する版は処理が終わるまで保持し、イベント、要約、配信記録も処理完了後は最新の完了結果だけを残す。 |
| FR-030 | サイトアダプターは求人タイトルを必須メタデータとして抽出し、求人HTMLの版とともに保存する。タイトルまたは求人固有領域を抽出できないページは解析失敗とする。 |
| FR-031 | 利用者の通知時刻までに確定した新着、更新、掲載終了を1回の通知ダイジェストにまとめ、求人ごとの要約を維持する。チャネルの上限を超える場合だけ複数メッセージへ分割する。 |
| FR-032 | 要約生成が最終失敗した求人は、イベント種別、機械抽出した求人タイトル、求人URLを使って通知する。 |
| FR-033 | 同じ求人に複数イベントが通知前に発生した場合は最新状態へ集約する。新着後の更新は最新内容の新着、新着後の掲載終了は通知なし、更新後の掲載終了は掲載終了、掲載終了後の再掲載は再掲載とする。複数更新は最後に通知した版と最新の版を比較する。 |
| FR-034 | 新しい監視設定の既定の確認・通知間隔は24時間とし、利用者が12時間へ変更できる。 |
| FR-035 | 掲載終了が確定した求人は単独の定期詳細確認を停止し、有効な監視設定の検索結果へ同じ求人IDが再出現した場合だけ詳細を再確認する。 |
| FR-036 | 検索結果の巡回がサイト別の最大ページ数または最大求人件数を超えた場合は部分結果を確定せず、監視設定を`NEEDS_ATTENTION`として停止する。利用者が検索条件を修正して再開した場合は通知なしで再基準化する。 |
| FR-037 | 求人タイトルは最新表示用メタデータとして正常取得ごとに更新するが、比較用ハッシュには含めない。タイトルだけの変化では新版、更新イベント、通知を作成しない。 |
| FR-038 | 抽出ルールの版を更新した場合は、新旧版のハッシュを比較せず、対象サイトの求人を通知なしで再基準化してから通常の変更検知を再開する。再基準化に失敗した求人は旧版を維持して個別に再試行する。 |
| FR-039 | LINE通知のON・OFFにかかわらず、求人の現在版に対する現在要約を生成してWeb画面へ表示する。LINE通知がOFFの場合は外部配信と変更要約の生成を行わず、後からONにしても過去イベントを遡って通知しない。 |
| FR-040 | 求人の現在版ごとに利用者間で共有する現在要約を保持し、更新通知では利用者へ最後に通知した版と現在版から通知項目単位の変更要約を生成する。 |
| FR-041 | 利用者はアカウントを削除できる。削除時は認証ID、Webセッション、監視設定、通知先、利用者と求人の関連、未送信ダイジェスト、利用者向け処理中作業を削除または中止する。他利用者が参照する求人データは維持し、参照も処理中作業もない求人は削除する。 |
| FR-042 | 通常通知枠は利用者のタイムゾーンで、24時間設定では毎日9:00、12時間設定では毎日9:00と21:00とする。初期タイムゾーンは`Asia/Tokyo`とし、処理遅延で次回枠をずらさない。 |
| FR-043 | 通常枠までに通知可能にならなかったイベントは遅延イベントとして蓄積し、1時間ごとに通知可能な分を別の遅延ダイジェストへまとめる。要約が最終失敗した場合は求人タイトルとURLを使用する。 |
| FR-044 | 利用者のタイムゾーンで22:00から翌8:00までは外部通知を配信しない。取得、変更検知、要約、再試行は継続し、蓄積した遅延イベントを8:00以降の最初の遅延確認でまとめて通知する。 |
| FR-045 | 同じ求人サイトで解析失敗が設定回数または設定割合を超えた場合は、サイト単位のサーキットブレーカーを開いて取得を停止する。停止中は求人状態とイベントを確定せず、アダプター修正後に通知なしで再基準化してから再開する。 |
| FR-046 | Codex CLIには1回ごとの入力、出力、実行時間と、システム全体の日次・月次利用量の設定可能な上限を設ける。上限到達時はタイトルとURLへフォールバックし、変更検知と通知を遅延させない。 |
| FR-047 | 要約対象のcanonical HTMLが1回の入力上限を超えた場合は見出し・項目単位で決定的に分割して要約を統合する。合計処理量上限を超えた場合はタイトルとURLへフォールバックするが、求人版と変更イベントは有効なまま維持する。 |
| FR-048 | 利用規約やrobots.txtなどの取得許可条件が変更され取得不能になったサイトは、新規登録と全取得を停止する。既存求人を掲載終了扱いにせず最後の状態を維持し、再許可確認後に通知なしで再基準化してから再開する。 |

## 非機能要件

| ID | 要件 |
| --- | --- |
| NFR-001 | 新しい求人サイトは、サイトアダプター、明示的な登録コード、契約テスト用HTMLを追加することで対応できる。 |
| NFR-002 | 取得、変更保存、イベント生成、通知依頼は再実行しても重複する結果を作らない。 |
| NFR-003 | サイト単位の同時実行数、最小アクセス間隔、タイムアウト、再試行を設定できる。 |
| NFR-004 | robots.txt、利用規約、認証要否をサイト追加前に確認し、許可された範囲だけを取得する。 |
| NFR-005 | HTMLを信頼できない入力として扱い、Codex CLIの命令やシステム設定として解釈させない。 |
| NFR-006 | 監視対象、サイト、処理段階ごとに成功数、失敗数、所要時間、キュー滞留を観測できる。 |
| NFR-007 | 変更確定と通知依頼の間でイベントが失われない。 |
| NFR-008 | 共通ヘッダー、フッター、告知、広告など求人と無関係な変更では求人更新を検知しない。 |
| NFR-009 | 未処理の通知が参照するデータを削除せず、通常時の保存量は求人ごとに現在版と直前版へ収束させる。 |

## 受入条件

| ID | 条件 |
| --- | --- |
| AC-001 | 各サイト個別仕様に従って求人IDを抽出し、`source_key`との組で求人を一意に保存できる。 |
| AC-002 | 同じ検索結果を複数回処理しても、利用者と求人の組に対する`DISCOVERED`イベントと通知は1件だけである。 |
| AC-003 | 共通ヘッダー、フッター、告知、広告、動的tokenだけが変わったページでは更新と判定せず、求人固有領域が変わった場合は更新と判定する。 |
| AC-004 | 更新通知の要約処理は、直前版と新しい版の両方を参照できる。 |
| AC-005 | サイトアダプターが明確な掲載終了表示を判定したページは1回で論理削除される。HTTP 404は間隔を空けた2回連続の確認で論理削除され、1回だけの404、タイムアウト、429では論理削除されない。 |
| AC-006 | 新規サイトの追加時に、既存の変更検知、要約、通知コンポーネントを変更しない。 |
| AC-007 | GoogleのcallbackとID tokenを検証し、同じGoogle subjectでは同じ利用者としてログインできる。 |
| AC-008 | 検索結果URLと12時間または24時間を登録し、期限に従う取得作業を作成できる。 |
| AC-009 | LINE通知が未連携または利用不能でもGoogleログインと求人閲覧はでき、画面にOFFまたは要対応状態を表示する。 |
| AC-010 | 他利用者のIDを指定したHTTPリクエストで、その利用者のデータを取得・変更できない。 |
| AC-011 | load-more方式の一覧を終了まで処理し、追加表示された求人IDも利用者向け発見の照合対象にできる。 |
| AC-012 | 一覧から既存求人IDが消えても削除せず、詳細ページの明確な掲載終了表示、または間隔を空けた2回連続の404で削除する。 |
| AC-013 | 保存した求人HTMLに、詳細ページのヘッダー、フッター、共通告知、広告が含まれない。 |
| AC-014 | Googleログイン済み利用者がLINE通知をONにすると、LINE本人確認と友だち追加の完了後に通知先が有効になる。 |
| AC-015 | LINE callbackだけでは新しいJobHunter利用者を作成できず、Googleログイン済みの連携要求が必要である。 |
| AC-016 | LINE通知をOFFにしてもGoogleログインセッション、監視設定、利用者と求人の関連が維持される。 |
| AC-017 | 初回基準化で既存求人を保存しても`DISCOVERED`イベントと通知を生成せず、完了後に初めて現れた求人だけを通知する。 |
| AC-018 | 同じ求人が複数利用者または複数の監視設定に含まれても、同じ更新、削除、再掲載に対する求人状態イベントは1件だけである。 |
| AC-019 | 同じ利用者の複数の監視設定に同じ求人イベントが該当した場合、該当条件をまとめた通知を1件だけ配信する。 |
| AC-020 | 監視設定を停止するとその検索取得を行わず、再開時は通知なしで再基準化され、停止中の変化を通知しない。 |
| AC-021 | 通常状態では求人ごとのHTML版が現在版と直前版だけになり、未処理通知が参照する版だけが処理完了まで追加保持される。 |
| AC-022 | 求人タイトルを抽出できない詳細ページは解析失敗となり、求人版とイベントを確定しない。 |
| AC-023 | 同じ通知時刻に複数求人のイベントがある場合、新着、更新、掲載終了と求人ごとの内容を1回のダイジェストとして配信する。 |
| AC-024 | 要約が最終失敗しても求人タイトルと求人URLを含む通知を配信する。 |
| AC-025 | 新着から掲載終了まで通知前に進んだ求人は通知せず、複数回更新された求人は最後に通知した版と最新の版の差分だけを通知する。 |
| AC-026 | 新しい監視設定の入力画面では24時間が初期選択され、12時間を選んで登録することもできる。 |
| AC-027 | 掲載終了求人の詳細取得作業は定期投入されず、検索結果へ同じ求人IDが再出現した場合だけ再掲載確認が行われる。 |
| AC-028 | 検索巡回がサイト別安全上限へ達した場合は求人を1件も確定せず、監視設定が要対応として停止される。 |
| AC-029 | 求人タイトルだけが変化した詳細ページでは最新タイトルを更新するが、求人版と`UPDATED`イベントを追加しない。 |
| AC-030 | `extractor_version`更新後の再基準化では更新通知を生成せず、完了後に同じ版同士の比較で変更検知を再開する。 |
| AC-031 | LINE通知がOFFでも現在要約がWeb画面へ表示され、ONに戻してもOFF期間中のイベントは配信されない。 |
| AC-032 | 同じ求人を複数利用者が閲覧すると現在版の現在要約を共有し、更新通知では各利用者の最終通知版に応じた変更要約を使用する。 |
| AC-033 | アカウント削除後はその利用者のセッション、監視設定、通知先、求人関連、未送信ダイジェストへアクセスできず、他利用者が参照する求人は維持される。 |
| AC-034 | 24時間設定は9:00、12時間設定は9:00と21:00を次回通知枠とし、前回処理の終了時刻によって枠がずれない。 |
| AC-035 | 通常枠に間に合わなかったイベントは遅延分として蓄積され、通知可能になった後の1時間ごとの確認で通常分と別に配信される。 |
| AC-036 | 22:00から翌8:00まで外部配信されず、休止時間中に通知可能となった遅延イベントが8:00以降に1件へまとまる。 |
| AC-037 | サイト単位の解析失敗閾値を超えると、そのサイトの取得作業が停止し、求人状態とイベントが更新されない。 |
| AC-038 | Codex CLIの日次または月次利用量上限へ達しても、タイトルとURLを使ったWeb表示と通知が継続する。 |
| AC-039 | 入力上限を超えるcanonical HTMLは決定的な同じ単位へ分割され、合計上限超過時も求人版とイベントを破棄しない。 |
| AC-040 | 取得許可を失ったサイトの求人は掲載終了にならず、監視設定に取得不可が表示され、再許可後は通知なしで再基準化される。 |
